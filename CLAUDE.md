# CLAUDE.md — build instructions for this repo

These are the working instructions I used with Claude Code to build this project. They are
committed deliberately: the brief asks for the instruction stack, and this is half of it.
The other half — the run-time prompt that writes the briefing — lives in `prompts/`.

Anyone (human or agent) picking this repo up should follow what's below.

---

## What this is

A monthly S&OP briefing generator for Manukora. It turns four months of SKU-level sales and
inventory data into a briefing a non-technical executive can read in five minutes and act on.

Built for a practical exercise. The mock data is committed under `data/`.

---

## The one architectural invariant

**The LLM never does arithmetic.**

Every number is computed in `src/engine.py`, validated by tests, and serialised to
`facts.json`. The model receives those facts and writes prose around them. It cannot compute,
estimate, or infer a figure.

This is not a style preference. It is what makes the output verifiable, and it is the claim
the whole design rests on. If you find yourself letting the model calculate something —
even a percentage, even a difference of two numbers already in the fact pack — stop and move
that computation into the engine.

`tests/test_output_integrity.py` enforces this: every figure in the generated briefing must
trace back to `facts.json`.

---

## Hard rules

### 1. No hand-typed figures. Anywhere.

No number is typed by hand into any document in this repo — not the README, not the runbook,
not the architecture write-up, not a commit message. Every figure is copied from `facts.json`
or generated by the engine.

This rule exists because it was broken. While planning this project I wrote two illustrative
figures into the design document — a "22% of total revenue" that was actually 16.6%, and a
"~1,150 units" reorder example that the project's own formula puts at 934. Both were
plausible. Both were wrong. Both were written into the same document that proposed a test
against exactly this failure.

If a number is needed for prose, run the engine and read it off. If that feels like too much
friction for a single figure, that friction is the point.

**The one figure the engine cannot produce** is the size of the test suite, which the README
quotes twice. It has no fact pack to be read off, so the rule was quietly suspended for it —
and it drifted. Not by being wrong when written: it was correct for four commits, and then
two later commits each added tests without touching the README. That is the whole failure
mode. A figure nobody has to update stays right until it silently does not, and the moment
it turns is invisible.

A hand-typed figure is admissible only where something checks it. `tests/test_docs_claims.py`
compares every count the documentation states against the suite that actually ran, so this
one is now maintained by the build rather than by whoever remembers.

### 2. Business rules live in `config.py` and nowhere else

Target cover overrides, phase-out SKUs, launch dates that invalidate early months, supplier
lead times — all of it is declared in `src/config.py` with a comment explaining the source.
No rule is inlined in `engine.py`, and none is implied by a magic number.

A reviewer must be able to read `config.py` alone and know every business assumption in play.

### 3. Assumptions are declared, never buried

Where the brief is silent, the code assumes and says so. Supplier lead time is the clearest
case: it is not in the data, so it is inferred and documented — in `config.py`, in the
README, and in `OPEN-QUESTIONS.md` as something to confirm with the stakeholder.

Silent assumptions are the failure mode this whole exercise is about.

### 4. Months are named, never coded

The dataset uses `M1`–`M4`. The output says "December 2025" through "March 2026". `M4` is a
column name, not something an executive should have to translate.

### 5. Document as you go

Each branch updates the documentation it affects, in the same branch. Documentation is not a
final phase. A commit history of silent code followed by one large docs dump is exactly the
thing this repo is trying not to be.

## Security

- No credentials, keys, tokens, customer data or supplier data. Ever.
- `.env` is gitignored; `.env.example` carries the shape, never a value.
- The engine, all tests, and the `--no-llm` briefing run with no API key at all. A reviewer
  should be able to clone and run everything without secrets.

---

## Git conventions

- Conventional commits: `feat:`, `test:`, `docs:`, `fix:`, `chore:`.
- One logical change per commit. Small and readable beats tidy-in-hindsight.
- Work happens on branches; `main` gets merges.
- Every PR gets a description explaining *why*, not just what changed.

---

## Verification before any claim of "done"

1. `pytest` green.
2. `python -m src.main --no-llm` produces a complete briefing with no API key.
3. Every figure in the output traces to `facts.json` (`test_output_integrity.py`).
4. No secrets in the diff.
